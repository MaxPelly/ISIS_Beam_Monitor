# ISIS Beam Monitor Codebase Documentation

This document provides a technical overview of the ISIS Beam Monitor codebase, its architecture, components, and guidance for future development.

## Architecture Overview

The ISIS Beam Monitor is a real-time monitoring system designed to track accelerator beam status and MCR (Main Control Room) news updates at the ISIS Neutron and Muon Source. It follows a decoupled, asynchronous architecture using Python's `asyncio` for concurrent operations.

### High-Level Design
The system uses a two-tier architecture (daemon and client) communicating via local UNIX domain sockets:
1.  **Daemon**: A long-lived background process holding the master `DaemonState` (in `daemon_state.py`). It orchestrates monitors, persists state to a local SQLite database (`storage.py`), and serves multiple clients via JSON over IPC (`ipc.py`).
2.  **Monitors**: Asynchronous tasks that fetch and process data from external sources (WebSockets for beam data, HTTP polling for MCR news). They report into the `DaemonState` passed to them as `sink` (a mock in tests).
3.  **Notifications**: `isis_monitor/messages.py` builds channel-agnostic `Notification` objects (title, severity, emoji, facts, optional URL) for every notification-worthy event; `notifiers.py` renders and delivers them (e.g. as Microsoft Teams Adaptive Cards) via `NotificationChannel`s.
4.  **TUI Client**: A terminal UI built with the `rich` library. It acts as an IPC client, fetching the initial state snapshot from the daemon and then subscribing to a real-time event stream to update its display. It can also edit a subset of the config over IPC; the daemon validates and saves it, then re-execs itself to apply it.

## Component Deep Dives

### `isis_monitor/beam.py`
The core logic for accelerator beam monitoring.
-   **`BeamMonitor`**: Manages the single WebSocket connection. It subscribes to the three beam-current PVs plus every instrument's counts, run-name, run-state, run-number and RB-number PVs, with one route table (`routes`, PV → handler, built from the beam targets and each tracker's `pv_handlers()`, and subscribed in that order). Each handler comes from `instrument.on_field()`, which skips PVWS's partial updates that lack the PV's field (e.g. a severity-only one). Config validation guarantees no PV is shared. `run()` works until cancelled: it gathers the websocket loop (`_run_loop`, a plain `async for` over messages that reconnects after `beam_reconnect_interval`, or immediately when `request_reconnect()` closes the socket; `_classify_ws_error()` sorts failures into transient ones (dropped connections, timeouts, 5xx) and persistent ones (a rejected handshake, bad URL, TLS or DNS failure, or an unexpected error), which set beam health to `"error"` and double the retry wait up to `BEAM_MAX_BACKOFF` (300s, or the interval if that's longer) until the next successful connection; repeats of the same kind of failure are logged at debug, and one line summarises the outage on reconnect) with `_collection_check_loop`, which runs each tracker's stall check roughly every 60s (one failing tracker is logged and doesn't stop the others). A malformed PV update is logged and skipped rather than dropping the connection.
-   **Beam targets**: `config.BEAM_NAMES` ("TS1", "TS2", "Muons") is the one name of each target everywhere: config, state, history, cards, push topics and the Teams channel. `config.beam_name()` reads a config value case-insensitively (accepting "Muon"). Each target's PV and power boundaries are a `BeamTargetConfig` in `AppConfig.beams`, from the optional `[BEAM:<NAME>]` sections over `DEFAULT_BEAMS`.
-   **State Management**: Tracks current beam currents and power levels (off, low, medium, high) to detect transitions, plus per-target `since` timestamps; held in `BeamMonitor.beams` (one `BeamState` per target); `_beam_power(target)` lets trackers look up their instrument's beam.
-   **`BeamChangeAggregator`**: Debounces raw beam-state transitions for `debounce_seconds` before turning them into notifications, dropping ones that flap back to their original state, and noting when other targets went off in the same window (the three targets share one accelerator, so correlated trips are the common case, not an edge case).

### `isis_monitor/instrument.py`
Run and counts tracking for one instrument (one `InstrumentTracker` per `config.instruments` entry).
-   **`status.py`**: `build()`, a pure function of `DaemonState` (and each beam's `since`) giving the status the push site's Status page shows (layout: the push site's `status.py`, version 1): beams with their current, power and last 24h in 144 ten-minute bins (mean current, most common power), each instrument's view (run, counts, target, RB number), MCR news and health. A beam with no live reading is sent as `unknown` with no current, never 0; titles are cut to 200 characters, keeping 20 instruments well under the site's 64 KB limit.
-   **`StatusPublisher`** (in `status.py`): with `[PUSH] url` set (and not `--dummy`), `run_daemon` runs one; it POSTs the status, signed like push notifications (`notifiers.signed_json`), to the url plus `/status` every `sample_interval`, and soon after `DaemonState.on_change` (a beam's power, MCR news, health, a run completed) pokes it, at most once per `DEBOUNCE` (5s). Nothing queues: each send builds the latest status, and a failure is logged at debug.
-   **`runs.py`**: `RunTracker`, run detection by run number (`IN:<NAME>:DAE:RUNNUMBER`), which moves on (+1) when a run ends; an abort doesn't change it, and the run is begun again under it with a new `DAE:STARTTIME`. It's synchronous and driven by each update's time, so recorded sequences replay deterministically; its one timer (`call_later`) calls `tick()`. A run starts once the run state has been past BEGINNING (in `STARTED_STATES`; a begin can fail after 5s) under a new number for `SETTLE` (1s); a run that changes number completes, with its last credited counts as its final total. Counts are credited only while it's surely the run's: not while replaying, which `resubscribed()` and a NaN on RUNNUMBER or RUNSTATE start (an IOC or gateway outage) and which ends once each has come since (or `REPLAY_TIMEOUT` after a resubscribe). A run that ended unseen is completed once the replay is over, whatever order it came in, with the counts seen in SETUP for the next number as its final (waiting for them if needed; unknown if a run begins first or more than one passed). A new number first seen ENDING (just after a replay, or while its start settled) is adopted quietly at once, so its end is recorded. A run number not after the last completed one is ignored, and counts are only credited once the number has been seen. A changed STARTTIME under the same number is a re-begin. RB number changes end experiments (`exp_gen` stops a run being counted in two); a run in progress with nothing collected yet becomes the new experiment's. A first start mid-run with no saved state is adopted silently. Decisions are logged (with `log_prefix`) and passed to an optional `RunListener`. Its behaviour was checked against 2.9h of live data (all 166 run changes, their final totals and 44 re-begins), and `tests/data/runs/` holds windows cut from it.
-   **`instlist.py`**: `parse_instlist()` decodes `CS:INSTLIST` (base64 of NUL-padded hex of zlib-compressed JSON) into each instrument's PV prefix and beam target (None for MISC); `{}` with a warning if it's unreadable. `BeamMonitor` subscribes to it first and, for each configured instrument, sets the tracker's target station (`set_station()`: the config's `beam_target` wins, then the station, then `[PVS] instrument_target` with one warning) and, if the prefix differs, swaps the tracker's PVs, rebuilds the routes and sends PVWS a `clear` for the old PVs and a `subscribe` for the new. The last good list is cached in `DaemonState.instlist` (snapshot key `"instlist"`) and applied when `BeamMonitor` is created. Each tracker's effective target is mirrored into `DaemonState` (`update_beam_target()`), which the daily summary groups by.
-   **Shadow run detection (1.3.0rc1)**: each `InstrumentTracker` also feeds its PVs (plus `DAE:STARTTIME`) to a `RunTracker` with no listener, which only logs its decisions with a `[shadow]` prefix, for comparing with the cards the title and counts heuristics below send. Its state is saved under `"shadow"` in the tracker's snapshot, and a failure in it is only logged. It replaces the heuristics in 1.3.0.
-   **`InstrumentTracker`**: Handles its instrument's run-name PV and counts PV for new runs (a new-run card when the title changes, or when counts drop by more than 1 — the only sign of a new run whose title is unchanged, e.g. "Hidden"; a title change within `RESET_RETITLE_WINDOW` (2 minutes) of a counts-reset start just names that run, its card having gone out under the old title; after a title-change start, the previous run's total (`stale_counts`, saved with the run's progress) is ignored if re-sent before BEGIN resets the counts, and that reset doesn't start another run (`BeamMonitor` subscribes to titles before counts, so a run changed while disconnected is reported under its new title); each start does run-completion recording) and counts PV (the "run about to finish" card, sent once there are `ETA_MIN_HISTORY` (3 minutes) of samples and the fitted rate puts the run within `finish_warning_minutes` of the run's target (`run_target`, fixed by `_set_target()` at each run start: `notify_counts`, or with `auto_counts` the median from `auto_target()` of the last `AUTO_RUNS` (5) of the `AUTO_HISTORY` (7) recorded run totals, leaving out ones under `AUTO_SHORT_UAH` (1 µA·h) or `AUTO_SHORT_FRACTION` (25%) of their median, and `notify_counts` until `AUTO_MIN_RUNS` (3) remain), or else on passing it; it is sent once per run; before the target the rate fit runs at most every `ETA_CHECK_INTERVAL` (30s)), and `check_collection_progress()` for stall warnings, suppressed while its `beam_target` is off and, once `run_state` (from `IN:<NAME>:DAE:RUNSTATE_STR`) is known, outside `COUNTING_RUN_STATES` (RUNNING, VETOING). Run starts never come from the run state, as an automated run plan passes through ENDING and BEGINNING in seconds. A warned stall keeps its start through pauses and disconnects (`reset_stall_clock()`), and once counts rise again in the same run a "collection resumed" card follows. The finishing and stall cards name `run_number` (`IN:<NAME>:DAE:RUNNUMBER`); the new-run card doesn't, as the number changes at BEGIN in no fixed order with the title and counts, but it shows the new run's target, so `_start_run` saves the new run before sending it. `handle_rb_number()` sends an "experiment finished" card when the RB number changes, "0" (no experiment) included, from `exp_runs`/`exp_uah` (counted per run start for the experiment in `run_rb`, plus the run in progress unless it has nothing collected or began within `NEW_EXPERIMENT_RUN_WINDOW` (30s), when it's the new experiment's first, as an automated run's PVs come in no fixed order) and `exp_since` ("at least" when `exp_partial`: the daemon first saw that RB number rather than its change, or the change came in the first RB value after (re)subscribing, `rb_resync`, so happened unwatched; that marks both experiments); "0" and an experiment with no runs get none.
-   **`InstrumentState`**: run name, start time, counts, `counts_reset_at` and `stale_counts` (above), `run_target` and `auto_runs` (the card says "(auto)" when it's above 0), for auto targets `run_totals`, and for every instrument `rb_number` (from `IN:<NAME>:DAE:_RBNUMBER`, subscribed before titles and counts; a change clears `run_totals` but leaves the old experiment's last run its target, while a run taken as the new experiment's first gets the new (fallback) one; a restart keeps each run's saved target unless `notify_counts` or `auto` changed, and blank is ignored) and `run_rb` (the RB number at the run's start: a total is only recorded for that experiment, so an old experiment's last run, only completed when the next one starts, isn't counted in the new one's history; blank once counted, so it isn't counted again if that RB number comes back), the experiment's `exp_*` progress (saved via `DaemonState.update_experiment()`), and a 15-minute deque of `(time, counts_collected)` samples used for the finishing card's rate/ETA ("target reached" when it was only sent on reaching the target). Counts come from the instrument's `counts_pv`, derived as `IN:<NAME>:DAE:TOTALUAMPS`: a numeric `value` giving the total µA·h collected this run (0 at the start of a run is a real reading; NaN is ignored).

### `isis_monitor/mcr.py`
Handles MCR news polling.
-   **`MCRNewsMonitor`**: Polls the news feed at a configurable interval until cancelled. It uses regex to parse the feed and detect changes in the latest news entry; `request_reconnect()` wakes the poll wait early.
-   **Adaptive Polling**: Implements exponential backoff on fetch failures to reduce load on the source during outages.
-   **Severity classification**: `messages.mcr_news()` classifies each update as GOOD/ATTENTION/WARNING/INFO by keyword (see `messages.py` below) and can attach an "Open MCR news" link via `[DATA] mcr_page_url`.

### `isis_monitor/messages.py`
Builds the structured, channel-agnostic notifications used everywhere else.
-   **`Notification`**: A dataclass (title, text, severity, emoji, facts, url/url_label, timestamp, topic, beam) with a `to_plain_text()` method used by `DummyNotifier` and log lines.
-   **`Severity`**: `INFO` / `GOOD` / `WARNING` / `ATTENTION`, mapped to Adaptive Card container styles by `notifiers.py`.
-   **Builders**: one pure function per notification-worthy event — `beam_change`, `startup_status`, `run_started`, `run_finishing`, `collection_stalled`, `collection_resumed`, `experiment_finished`, `mcr_news`, `daily_summary`. They are pure and deterministic, and take keyword arguments after the first. The run builders take the instrument name as their first argument and prefix it to the title. Beam cards and daily summaries set `beam` to the target's label.
-   **`fmt_time` / `fmt_duration` / `set_timezone` / `get_timezone`**: shared formatting helpers; the display timezone is process-global, set once from `[NOTIFICATIONS] timezone` at startup.

### `isis_monitor/summary.py`
Daily per-target uptime summaries.
-   **`compute_summary(history, since, until=None, sample_interval=60.0)`**: a pure function over `DaemonState.history`'s samples, returning each target's uptime %, trip count, longest continuous on-streak, a sparkline of the whole window (averaged into 60 bins, via `messages.sparkline_chars`) and `coverage_pct`, the share of expected samples actually recorded. Samples aren't recorded while the beam feed is down, so uptime covers only the time the beam could be seen, an on-streak ends at a gap longer than 3 sample intervals (at least 3 minutes, so a daemon restart doesn't end one), and a trip that starts and ends inside a gap isn't counted; the card adds a "Data coverage" fact when coverage is under 99%.
-   **`daily_summary_loop`**: runs inside `run_daemon`, checks the configured local time (`[NOTIFICATIONS] summary_time`) once a minute, and sends one card per target when it's reached (its "Runs in last 24h", and a line per instrument with its runs and µA·h from `runs_completed_since()`, cover only instruments whose `beam_target` is that target) (deduped to once per day via the `"summary_last_sent"` snapshot key, so a restart doesn't resend).

### `isis_monitor/notifiers.py`
A decoupled notification system.
-   **`Notifier` (Abstract)**: Base class for notification implementations; `send()` takes a `Notification`.
-   **`HTTPNotifier`**: Base for notifiers that POST JSON: subclasses provide `_create_payload()` (and may override `_request_kwargs()`), and it handles the session, retries and `Retry-After` described under `TeamsNotifier`.
-   **`TeamsNotifier`**: Renders a `Notification` as a Microsoft Teams Adaptive Card (severity-coloured header, body text, `FactSet`, a small footer with the time and the monitor's version, optional `Action.OpenUrl` button) and posts it via webhook. A 429, a 5xx or a network error/timeout is retried after `RETRY_DELAYS` (2s, then 4s: three attempts in all), or after the server's `Retry-After` (seconds or HTTP date) capped at `MAX_RETRY_AFTER` (60s); other 4xx responses aren't retried. Its worker waits during retries, so its later notifications are delayed (bounded by the attempts, `webhook_timeout` and the delays), but other notifiers and callers aren't.
-   **`WebhookNotifier`**: POSTs the `Notification` as versioned JSON (`"v": 1`, a fresh `id`, its fields including `topic`; not the Teams-only `summary` and `channel`) signed with `X-Timestamp` and `X-Signature` (hex HMAC-SHA256 of `<timestamp>.<body>`). Each attempt is re-signed but keeps the `id`, so a receiver can drop repeats. `[PUSH] url` adds one shared notifier to every channel, so the feed keeps the order notifications were sent in, with a short `timeout` (2s default) and the same retries as Teams.
-   **`NotificationChannel`**: Groups multiple notifiers for a specific category of updates (e.g., "Beam Updates"), with a `route` that picks the Teams payload's `channel`, which downstream Power Automate flows route on: `main.build_channels` routes beam cards and summaries by their `beam`, run cards to "Experiment Updates" or, for an instrument with `channel = instrument`, its name, and MCR news to "MCR News" (the channel's own name, the default). `broadcast()` is synchronous: it queues the notification and its route on each notifier and returns. Each `Notifier` has its own queue (bounded at 100; the oldest is dropped with a warning when full) and worker task, which sends them in order, so a slow or hung webhook never holds up the caller (in particular the beam WebSocket loop, which would otherwise stop reading and miss keepalive pongs) or any other notifier. A failing send is logged and the worker carries on. `build_channels` creates the notifiers and one aiohttp session they share; `run_daemon` closes each notifier once, all within `CLOSE_TIMEOUT` (5s) to send what's queued, then the session. Notifications queued after a notifier closes are logged and dropped.

### `isis_monitor/tui.py`
The live terminal interface.
-   **`RichTUI`**: Coordinates the layout and rendering. All updates arrive on the event loop from the IPC event stream (`main.tui_connection_loop`); history comes from the daemon's `sample` events.
-   **Compact layout**: below `COMPACT_WIDTH` (80) columns `_make_layout()` builds a phone-sized layout (header, beams on one line, two lines per instrument, MCR news) with no graph or logs panel; their updates return early but the data is still kept. `set_compact()` rebuilds the layout and swaps it into Live; `main.run_tui` calls `fit_to_width()` at start and on `SIGWINCH`, and the `v` key calls `toggle_compact()`, after which resizes no longer change the layout.
-   **`_render_sparkline()`**: wraps `messages.sparkline_chars(values, width)`, the pure, uncoloured renderer shared with `summary.py`, adding per-block colour.
-   **Instruments panel**: `set_instruments()` (from the snapshot) and `update_instrument()` (from `run`/`counts` events) (and `target` events) feed a table of run name and a progress bar towards the run's `target` (marked ≈ when it came from recent runs, `auto_runs` > 0), capped at 8 rows plus "+N more".
-   **Keys** (`main.run_tui`): stdin is in cbreak mode and read with `os.read` (not `sys.stdin`, whose buffer can swallow keys or block the loop). `c` hands the terminal to the config editor: the key reader is removed, Live is stopped and canonical mode restored, then everything is put back when the editor exits (or skipped if the TUI is quitting). Keys read in the same chunk as `c` are passed to the editor as `typed_ahead`.

### `isis_monitor/config_editor.py`
The line-based editor behind the TUI's `c` key. `edit_settings()` works on the `editable_settings()` dict (numbered menu, add/edit/delete instruments, diff via `describe_changes()`, confirm before save); `run_config_editor()` fetches it with `get_config` and saves with `update_config`, returning to the menu with edits intact on `invalid_config` or a lost connection. Terminal I/O (`read_line`, `write`) and the request function are injected, so it is tested with scripted input; `main.run_tui` supplies a request function that always uses the currently connected client.

### `isis_monitor/daemon_state.py` & `storage.py`
The core state management and persistence layer.
-   **`DaemonState`**: An event-loop-confined object (not thread-safe; `main.StateLogHandler` hands off log records from other threads via `call_soon_threadsafe`) holding current beam statuses, historical data buffers, MCR news, health checks and recent run completions. It holds no instrument state: each `InstrumentTracker` is the only record of its own, with `to_snapshot()`/`from_snapshot()` (a `format` number; an entry that's malformed or from an older version is logged and ignored) and `view()` (the snapshot plus the effective `beam_target`). `DaemonState.instruments` is a callable, set by `run_daemon` to `BeamMonitor.instrument_views`, that the snapshot, IPC `get_snapshot` and the daily summary read; `saved_instruments` holds the restored entries for configured instruments (`instrument_names`) until `BeamMonitor.restore_instruments` hands them to the trackers. `record_run_completed(instrument, ts, run_number, uah)` and `runs_completed_since(since, instruments)` track completions and the µA·h each collected; the last `RUN_COMPLETIONS_WINDOW` (24h) of them persist across restarts via the snapshot, so the daily summary's run counts survive a restart. It manages a pub/sub queue system for IPC clients (beam, sample, MCR, health and log events; the TUI re-reads instruments from `get_snapshot` every 2s): a subscriber whose queue fills is dropped and sent a `None` sentinel, so its connection closes and the client resyncs. `update_health()` only publishes actual status changes; any beam health other than `"connected"` also sets every beam's power to `"unknown"` (keeping its last current), and restored beam states start as `"unknown"` too, so stale values never look live. PVWS re-sends every value on reconnect.
-   **`SQLiteStateStore`**: Persists beam samples (one per `sample_interval`) and JSON snapshots (`"daemon_state"`, which also caches the last `CS:INSTLIST` as `"instlist"`, and `"summary_last_sent"`), enabling crash recovery and historical lookups. `main.state_persistence_loop` writes to it every `sample_interval` (recording beam samples only while beam health is `"connected"` and skipping beams still `"unknown"` just after a reconnect, leaving a gap in the history otherwise), logging and retrying on any error rather than crashing the daemon (the daily summary loop likewise logs a failed summary and carries on). All async access goes through `store.run(fn, ...)`, which uses a single worker thread: the connection is shared, and concurrent use from several threads corrupts it. The snapshot also carries each instrument's `run_started_at` and `end_notified` (kept on restore only if the instrument's `notify_counts` and `auto` are unchanged, since a card for another target doesn't cover the new one), which `run_daemon` restores into the trackers (via `BeamMonitor.restore_instruments`) so restarts don't reset a run's clock or re-send its finishing card; connection health is live state and isn't saved.

### `isis_monitor/ipc.py`
Manages local communication between the daemon and clients.
-   **`IPCServer`**: A UNIX domain socket server speaking newline-delimited JSON, created owner-only (0600). Methods: `get_snapshot` (with the daemon's `version`, shown in the TUI header), `get_history` (optional `limit` = newest N samples per beam), `get_logs`, `subscribe_updates`, `command` (`force_reconnect_all`, `shutdown`), and — via the optional `config_handler` — `get_config` (editable settings read fresh from the file, a `revision` hash, and the allowed `beam_targets` and `channel_modes`) and `update_config` (`settings` plus that `revision`; errors `invalid_config`, `config_changed`, `restart_pending`, `invalid_request`, `config_write_failed`). Malformed or failing requests get an `ok: false` reply without dropping the connection. `stop()` closes attached clients itself, since Python 3.12's `Server.wait_closed()` otherwise waits for them forever, gives them `STOP_FLUSH_TIMEOUT` (1s) to take already-written replies (e.g. to the `update_config` that triggered a restart), then aborts any that aren't reading. A subscriber whose event queue overflows, or which takes nothing for `SUBSCRIBER_DRAIN_TIMEOUT` (30s), is aborted; the client reconnects and resyncs.
-   **`IPCClient`**: One background reader task routes replies and pushed events to separate queues, so `request()` and `iter_events()` can run concurrently. Once the connection ends, every later call raises instead of hanging. `request(..., timeout=)` closes the client on timeout, since a late reply would otherwise be taken as the next request's answer; the TUI's sync (which subscribes before fetching state, so no event is missed) and `main.py stop` use `IPC_REQUEST_TIMEOUT` (10s). Reconnection backoff lives in `main.tui_connection_loop`.

### `main.py` — restarting the daemon
`run_daemon` returns `True` when a restart was requested (a successful `update_config`; config edits are serialised with a lock and refused once a restart is pending). `main()` then, after the lock, database and socket are released, calls `restart_process()`: it flushes output and `os.execve`s the same interpreter and `sys.orig_argv`, keeping the PID, with `ISIS_MONITOR_RESTARTED=1` so the new process ignores `-n/--notify_current`. If exec fails it prints the error and exits 1. Tests make `os.execve` raise via an autouse fixture, since a real exec would replace pytest.

## Configuration

Configuration is managed via `config.ini` files, loaded through `isis_monitor/config.py`. Key sections include:
-   **`[DATA]`**: WebSocket and HTTP URLs for data sources, plus the optional `mcr_page_url` link button.
-   **`[WEBHOOKS]`**: URLs for Teams integration (should be kept secure). A blank URL disables that channel's Teams notifier.
-   **`[PUSH]`**: meant for the optional `push_site` git submodule (a separate repo and a PWA that sends mobile Web Push; it never imports this package, and the signed payload is the only contract). Settings are optional `url`, `secret_file` and `timeout` for the `WebhookNotifier`. `parse_config()` only checks `url` and that `secret_file` is set; `main()` reads the secret with `read_push_secret()` in daemon mode only (the TUI and `stop` never need it), into `AppConfig.push_secret` (left out of `repr`): 32 to 4096 characters (the push site's limits) once surrounding whitespace is dropped, warning if the file is world-readable. These keys aren't TUI-editable.
-   **`[INSTRUMENT:<NAME>]`**: one per instrument — `notify_counts` (required, µA·h, or `auto, <fallback>` for `InstrumentConfig.auto_counts`), `beam_target` (None if unset: the tracker's effective one comes from `CS:INSTLIST`) and `channel` (`experiment`/`instrument`, both optional); at least one is required; parsed into `AppConfig.instruments` (`InstrumentConfig`, with its PVs derived as `pv_prefix` (`IN:<NAME>:` until `CS:INSTLIST` says otherwise) plus `DAE:` and `TOTALUAMPS` (`counts_pv`), `WDTITLE` (`run_name_pv`), `RUNSTATE_STR` (`run_state_pv`), `RUNNUMBER` (`run_number_pv`) and `_RBNUMBER` (`rb_number_pv`)).
-   **`[PVS]`**: `instrument_target` (TS1): the `beam_target` for instruments that don't set one and that `CS:INSTLIST` doesn't put on TS1, TS2 or MUON.
-   **`[DAEMON]`**: Paths for the UNIX socket, lock file and SQLite database (relative paths, like `[LOGGING] file` and `[PUSH] secret_file`, are resolved against the config file's directory, keeping them out of shared `/tmp`), and retention settings. **`[TUI_CLIENT]`**: the TUI's reconnect backoff.
-   **`[BEAM:<NAME>]`**: one optional section per target (TS1, TS2, Muons): its current `pv` and power `boundaries` (finite and non-decreasing).
-   **`[TUI]`**: Display settings like history length and refresh rates.
-   **`[NOTIFICATIONS]`**: `timezone` (for card timestamps and `summary_time`), `debounce_seconds` (beam-change confirmation window, 0–3600), `stall_minutes` (collection-stall warning threshold, up to 7 days), `finish_warning_minutes` (how far ahead of `notify_counts` the finishing card is sent; 0 = only on reaching it), and `summary_time` (HH:MM local time the daily summary is sent).

`load_config()` is a thin wrapper over `parse_config(parser, path)`, which also validates everything that could otherwise fail only after a restart (timezone, finite bounds, instrument names and PV clashes). `editable_settings()` exposes the TUI-editable subset (the `[NOTIFICATIONS]` keys above and each instrument's name, `notify_counts`, `beam_target` and `channel`) as INI strings; the daemon's `get_config` adds the allowed `beam_targets` and `channel_modes`; `update_config_file()` applies such a dict, validates the result, checks the file still matches the given revision (from `read_config()`), then writes it atomically (temp file, `fsync`, `os.replace`, directory `fsync`), keeping the file mode and a `.bak` copy. `configparser` drops comments on rewrite.

## Customizing the TUI Layout

The TUI is built using `rich.layout.Layout`. You can adjust the proportions and sizes of the interface by modifying `isis_monitor/tui.py`.

### Adjusting Section Sizes
In `RichTUI._make_layout()`, sections are defined using `split_column` and `split_row`.
- **Fixed Height**: Use the `size` argument (e.g., `Layout(name="header", size=3)`) to set a fixed number of rows.
- **Proportional Width/Height**: Use the `ratio` argument (e.g., `Layout(name="left", ratio=1)`) to make a section take up a proportion of the available space.

### Column Widths & Internal Padding
- **Table Columns**: The beam status table in `_update_beam_panel()` uses `expand=True`. To adjust individual column behaviors, modify the `table.add_column()` calls.
- **Graph Width**: The TUI automatically scales sparklines using `shutil.get_terminal_size()`, but you can override `SPARK_WIDTH` in `_update_beam_graph()` if you want a fixed size.

## Advice for Future Changes

### Future Considerations
-   **aiosqlite (deliberately deferred)**: `storage.py` runs every SQLite call on one worker thread via `store.run()`. The load is tiny (three beam rows and one snapshot per `sample_interval`, plus the daily summary), and the single thread already solves the connection's thread-safety problem, so moving to `aiosqlite` would add a dependency and a rewrite of `storage.py`, both loops and their tests for no measurable gain. Revisit it only if persistence becomes measurably slow, e.g. `state_persistence_loop` ticks overrunning `sample_interval`.

### Potential Features
-   **Prometheus Exporter**: Add a lightweight HTTP endpoint to export beam metrics and health status for ingestion by Prometheus/Grafana.
-   **Interactive TUI**: The TUI already has `r` (reconnect) and `c` (config editor) and `v` (compact/full layout); further shortcuts could toggle specific notification channels. The editor only covers `[NOTIFICATIONS]` and instruments; extending `EDITABLE_NOTIFICATION_KEYS`/`editable_settings()` would expose more (keep secrets like webhook URLs out of it).
-   **Multiple Notifiers**: Add support for Email, Slack, or SMS notifiers by implementing the `Notifier` interface.

### Best Practices for Extension
1.  **Async/Await**: Ensure all blocking I/O (like networking or DB access) is handled asynchronously (or wrapped in `to_thread`, or `store.run` for SQLite) to prevent freezing the TUI or Daemon.
2.  **State Safety**: `DaemonState` and `RichTUI` are only touched from the event-loop thread. Code running in a worker thread must hand results back to the loop rather than mutating them directly.
3.  **Shutdown**: Monitors run until cancelled (`main.run_until_stopped`), so they need no stop-event plumbing; loops that write to SQLite instead watch `stop_event` so an in-flight write finishes before the store is closed.
4.  **Tests**: `isis_monitor/tests` runs with `pytest` (pytest-asyncio in auto mode, so async tests need no decorator). Shared helpers live in `isis_monitor/tests/helpers.py`: `wait_until`, `FakePVWS` (a local PVWS stand-in, optionally on a fixed port), `running`, `serving`/`connected`/`raw_request` for IPC, `never_answers` and `fake_channel`. Prefer waiting on a condition over fixed sleeps.
